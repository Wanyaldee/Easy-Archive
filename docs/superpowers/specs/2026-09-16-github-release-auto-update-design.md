# GitHub Release連携アップデート機構 設計

## 背景・目的

バージョンを重ねていくにつれ、対象ユーザー（日本の学校・自治体の非エンジニア職員）が新しいリリースの存在に気づく手段がない。現状は`.deb`をGitHub Releaseへ手動配布しているのみで（ADR 0007）、更新は「GitHubを見に行って手動でダウンロードし直す」以外の方法がない。

対象ユーザーはターミナル操作をさせない方針（ADR 0007）であり、かつ本設計の前提として**利用者自身が自PCのsudo/管理者パスワードを持っている**（Active Directory等で管理者権限を持たない共有PC運用は今回のスコープ外）。この前提の下、GUIアプリ内から更新の検知・ダウンロード・インストールまで完結させる。

## スコープ

- 対象は**APTのみ**（Ubuntu系、`.deb`）。DNF（Fedora系）・Pacman（Arch系）等、他パッケージマネージャーへの対応は将来の拡張とし、今回は行わない。CLAUDE.mdの対象OS方針（Ubuntu系限定）とも一致する。
- 独自APTリポジトリの構築は行わない。GitHub Releasesの`.deb`アセットをそのまま利用する。
- CLIサブコマンドは追加しない。対象ユーザーはGUI経由のみを使うため、更新機能はGUI専用とする。

## アーキテクチャ

```
crates/
├── core/src/
│   └── update.rs   # 新規: バージョン比較・GitHub API問い合わせ・
│                    #       ダウンロード・チェックサム検証（GUI非依存）
└── gui/src/
    └── main.rs      # 既存のintegration_bannerと対になるupdate_bannerを追加
```

`crates/core`に置くのは、既存の`integration/`モジュールと同じ理由（CLI/GUI共用にできる形でロジックをGUI非依存に保つ）による。ただし今回はCLI側から呼ぶ予定はなく、テスト容易性（`crates/gui`はUIコードでユニットテストしづらい）を優先した配置である。

## データフロー

1. GUI起動時、バックグラウンドスレッド（`std::thread::spawn` + `mpsc::channel`。既存コードに非同期ランタイムがないため同じ流儀を踏襲）で`update::check_latest(current_version)`を呼ぶ。
2. `check_latest`は`GET https://api.github.com/repos/Wanyaldee/Easy-Archive/releases/latest`を`ureq`で呼び、レスポンスJSONから`tag_name`と`assets[]`（`.deb`のURLとチェックサムファイルのURL）を`serde_json`で取り出す。
3. `tag_name`の先頭`v`を除去し（例: `v0.2.0` → `0.2.0`）、`current_version`（`env!("CARGO_PKG_VERSION")`）と比較する。新しいバージョンがあれば`Some(UpdateInfo { version, deb_url, checksum_url })`をUIスレッドへ返す。取得できない・パースできない・同じかそれ以下の場合は`None`。
4. `None`の場合、あるいはネットワークエラーの場合は何も表示しない（起動時チェックは常に静かに失敗してよい）。
5. `Some`の場合、UIは`update_banner`（「新しいバージョン v0.2.0 があります」＋「アップデートする」ボタン）を表示する。
6. ボタン押下で別スレッドが`.deb`とチェックサムファイルを一時ディレクトリ（`std::env::temp_dir()`配下）へダウンロードし、SHA-256を計算して照合する。
7. 照合成功後、`Command::new("pkexec").args(["apt-get", "install", "-y", <deb_path>])`を実行する。
8. 終了コード0なら「再起動してください」ボタン付きの完了バナーに切り替える。再起動ボタン押下で`/usr/bin/easy-archive-gui`（`.deb`のインストール先として固定の既知パス。ADR 0007の教訓通り`current_exe()`はインストール直後は当てにならないため使わない）を新規プロセスとして起動し、自身は`std::process::exit(0)`する。

## バージョン比較

`semver`クレートは追加しない。本プロジェクトが発行するタグは`vX.Y.Z`のみでプレリリース識別子等は使わないため、`X.Y.Z`を`.`で分割して`(u32, u32, u32)`のタプルにパースし、タプル比較する手書き実装で十分（YAGNI）。パースに失敗した場合（タグ命名規則が将来変わった等）は「更新なし」として扱い、エラーにはしない（起動時チェックを壊さないことを優先）。

## 新規依存クレート

| クレート | 用途 | 追加の理由 |
|---|---|---|
| `ureq` | HTTPS通信（GitHub API・ダウンロード） | rustls採用でOpenSSL等の追加ネイティブ依存が要らない。同期APIで既存のスレッド+チャネル方針と相性が良い |
| `serde` / `serde_json` | GitHub APIレスポンスのJSONパース | `assets`配列を含むネスト構造の手書きパースは壊れやすく、標準的な選択 |
| `sha2` | ダウンロードした`.deb`のSHA-256検証 | root権限で実行する前の完全性検証として必須（ただし転送中の破損・改竄を防ぐのみで、ビルドパイプライン自体の侵害は防げない。GPG/minisign等のコード署名は本設計に含めておらず将来の課題。「既知の限界」参照） |

`crates/core`に追加する（`crates/gui`ではなく）。既存の`quick-xml`/`zip`等と同じ依存階層になる。

## インストール実行の詳細

- `pkexec`はシェルを介さずプロセスを直接起動するため、引数はエスケープ不要でそのまま渡せる。
- `dpkg -i`ではなく`apt-get install -y <deb_path>`を使う。`apt-get`はローカル`.deb`ファイルを指定してもAPTの依存解決の仕組みに乗るため、将来Depends対象のライブラリが増えた場合の保険になる（cargo-debの`Depends`は手動補完済みだが、二重の安全策として）。
- PolicyKitの認証ダイアログはOS標準のものをそのまま使う。カスタムpolkitアクション定義（`/usr/share/polkit-1/actions/`への`.policy`ファイル配置とダイアログ文言のカスタマイズ）は今回は追加しない。標準ダイアログはコマンドライン全体を表示するため非エンジニアには見慣れない文言になるが、機能上は問題なく、YAGNIとして将来の改善候補に留める。

## チェックサム検証とCI/リリース側への影響

現状の`v0.1.0`リリースのアセットは`.deb`のみで、チェックサムファイルが存在しないことを確認済み（`gh release view v0.1.0 --json assets`）。本機能を成立させるには、リリース時に`.deb`と併せてチェックサムファイル（`SHA256SUMS.txt`、`sha256sum`の標準出力形式）もアップロードする必要がある。

ADR 0007では「GitHub Releasesへのアップロード自動化は本マイルストーンの対象外」としていたが、本設計はその自動化とチェックサム生成を前提とするため、このアップデート機能のスコープに含める。

- 既存`.github/workflows/ci.yml`（ビルド検証のみ）の責務は変えず、タグpush（`v*`）をトリガーに`.deb`ビルド→`sha256sum`でのチェックサムファイル生成→GitHub Releaseへのアップロードを行う新規ワークフロー（`.github/workflows/release.yml`）を追加する。
- 現行の`v0.1.0`はチェックサムなしのため、本機能によるアップデート対象にはならない。次回リリース以降から機能する。

## エラーハンドリング

- 起動時の自動チェック: ネットワークエラー・API制限・パース失敗はすべて無視し、バナーを表示しないだけとする。ユーザーへの通知は行わない。
- 手動操作（ダウンロード〜インストール）の失敗は種別ごとにメッセージを分け、バナーに日本語で表示＋「再試行」ボタンを出す。
  - ダウンロード失敗（ネットワークエラー）: 「ダウンロードに失敗しました。ネットワーク接続を確認してください」
  - チェックサム不一致: 「ダウンロードしたファイルの検証に失敗しました。もう一度お試しください」（一時ファイルは削除する）
  - `pkexec`の認証キャンセル（終了コード126）: 「認証がキャンセルされました」
  - それ以外の非ゼロ終了: 「インストールに失敗しました」（詳細は握りつぶさずログには残すが、バナーには出さない）

## テスト方針

- `crates/core/src/update.rs`にユニットテストを書く:
  - バージョン比較（`0.1.0` vs `0.2.0`、`0.9.0` vs `0.10.0`のような桁上がり、不正フォーマット時に`None`を返すこと）
  - モックのGitHub APIレスポンスJSON文字列から`UpdateInfo`を正しく抽出できること（`.deb`アセットとチェックサムアセットの選別を含む）
  - 既知のバイト列とその既知のSHA-256値でのチェックサム検証ロジック
- 実際のHTTP通信・`pkexec`実行・PolicyKit認証ダイアログはユニットテスト対象外とする。ADR 0004/0005/0007と同様、実機（Zorin OS Core、VirtualBox仮想環境）で「バナー表示→ダウンロード→認証ダイアログ→インストール成功→再起動」の一連の流れを確認し、結果をADRに記録する。

## 既知の限界（将来の課題として明記）

- DNF（Fedora系）・Pacman（Arch系）等、APT以外のパッケージマネージャーへの対応はスコープ外（CLAUDE.mdの対象OS方針とも一致）。
- カスタムpolkitアクションによる認証ダイアログの文言改善は行わない。
- Active Directory等で管理者権限を持たない共有PC運用（利用者がsudoパスワードを持たないケース）は対象外。この場合は引き続き手動配布（IT管理者によるインストール）に頼る。
- **GitHub Releases APIの未認証レート制限（60リクエスト/時間/送信元IP）**: 本機能の起動時チェックはGitHub REST APIを未認証で呼ぶため、送信元IPごとに60リクエスト/時間の制限がかかる。実運用ターゲットである学校PC（1台のNAT越しIPの背後に多数の端末がぶら下がる構成が多い）では、始業時間帯など多数の端末が同じ時間帯に一斉起動すると、一部の端末は同じ1時間の枠内でこの上限を超えてしまう。この場合の失敗は「起動時チェックがサイレントに失敗しバナーが出ない」だけ（`check_latest`の設計通りfail-safe）で実害はないが、その時間帯はその端末群にとって機能が単に動かないことになる。本ブランチではこれを解決していない。チェック結果をローカルに24時間キャッシュする、あるいはAPIではなくレート制限のない静的なリリースアセットURLを直接叩く、といった対策は将来の課題として残す。
- **チェックサム検証は転送破損・改竄への対策であり、ビルドパイプライン自体の侵害への対策ではない**: 「新規依存クレート」表の`sha2`の注記の通り、`SHA256SUMS.txt`はダウンロードしたファイルが転送中に壊れたり差し替えられたりしていないことは検証するが、GPG/minisign等のコード署名は本設計に含めていないため、CI/リリースパイプライン自体が侵害された場合の防御にはならない。署名の追加は将来の課題として残す。
