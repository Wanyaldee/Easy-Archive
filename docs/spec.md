# Easy Archive 仕様書 / ADR

## 背景・目的

- ZorinOS導入済みの小学校PCで、自治体等から届くZIPファイル（中身のOfficeファイル名がShift-JIS）を通常の`unzip`で展開すると文字化けする。
- 現状はCLIでの回避策（`unzip -O cp932`等）を教えるしかなく、非エンジニアの教員には運用負荷が高い。
- Linux向けGUIアーカイバ（PeaZip, Xarchiver, Ark等）は文字コード自動判定機能を持たず、文字コードを正しく扱えるツール（unar -e, 7z+iconv等）はCLI限定という空白地帯がある。
- → GUI＋文字コード自動判定を両立したOSSツールをRustで作る。

## スコープ方針

- **対応フォーマットは当面ZIPのみ**。tar.gz等の他フォーマットは後回し。
- **解凍だけでなく圧縮機能も最低限備える**（相手にZIPを送り返す/自分で固めるケースがあるため）。
  - 圧縮時は既定でファイル名エンコーディングをUTF-8（汎用フラグbit11セット）にする。Shift-JIS等での圧縮出力は当面サポート対象外でよい（＝文字コード判定・変換ロジックが必要なのは解凍側のみ）。
- **第一段階はUbuntu系（Zorin OS含む）に限定**。他OS対応は後回し。
- コア部分（展開・圧縮エンジン・GUI）はOS非依存設計にしておき、将来のクロスプラットフォーム化に備える。
- 「文字コード解析」はファイル名/パスのデコードのみが対象。Office/バイナリファイルの中身はバイト列のまま書き出す/読み込むだけでよい（中身の変換は対象外）。
  - 検証済み: ZIP側のファイル名をCP932で正しく展開できていれば、内部のOfficeファイル（.doc/.xls/.ppt含む）自体は文字化けせず開ける。旧形式Office内部はOLE2/CFB構造でコードページ情報を保持しているため、アプリ側（LibreOffice等）が正しく解釈できる。よってZIP側の中身をバイト列として無変換で取り出す方針で問題ない。

## 技術検証結果: rc-zip vs zipクレート

`rc-zip`（bearcove/rc-zip, v5.4.1時点）のソースコードを直接確認し、以下の結論に至った。

| 項目 | 結果 |
|---|---|
| 判定粒度 | **アーカイブ全体で1回のみ**（`fsm/archive.rs`で全非UTF8エントリの名前/コメントをまとめて`chardetng`にfeedし、1つの`Encoding`を全エントリへ一律適用）。エントリ単位ではないため、1つのZIPに複数言語のファイル名が混在すると破綻する |
| 信頼度スコア | `chardetng::EncodingDetector::guess()`は`Encoding`型を1つ返すのみで、confidence値を返すAPIは存在しない |
| ライセンス | `Apache-2.0 OR MIT`（問題なし） |
| API安定性 | v5.4.1、活発にメンテナンスされている（2025年11月だけで6回リリース）が、メジャーバージョンが2→5まで進んでおり過去に破壊的変更あり |
| 対応エンコーディング | `Encoding` enumは`Utf8` / `Cp437` / `ShiftJis`の3種のみ。GBK・EUC-JP等は非対応 |
| 依存の重さ | `winnow`, `chardetng`, `encoding_rs`, `oem_cp`, `chrono`等。定性的に軽くはない。正確なバイナリサイズ影響は実測が必要 |
| 書き込み対応 | **非対応**（READメに"as of now, rc-zip does reading only"と明記） |

### 分岐判断: 自前実装 + `zip`クレートに一本化

上記の通り「エントリ単位判定」「信頼度スコア」の両方で要件を満たさず、rc-zipをそのまま使うと「複数言語混在ZIPで判定が破綻する」「GUI側で自動判定の自信度を表示できない」という当初の懸念がそのまま顕在化する。加えてrc-zipは読み取り専用なので、いずれにせよ圧縮側には別クレートが要る。

`zip`クレート（MITライセンス）は以下の理由で読み書き両方を任せられる:

- 読み書き両対応（圧縮もカバーできる）。
- `ZipFile::name_raw()`でファイル名を**生バイト列**（未デコード）のまま取得可能 → エントリごとに`chardetng`+`encoding_rs`で個別に文字コード判定できる。

よって **展開・圧縮ともに`zip`クレートに統一し、エントリ単位の文字コード判定を自前実装する**（rc-zipの`fsm/archive.rs`にある判定ロジックを、アーカイブ全体ループからエントリ単位ループへ書き換える形で流用可能）。rc-zip自体は採用しない。当初はこの自前実装に`chardetng`を使う想定だったが、後述のマイルストーン1実装時にこの方針を修正した。

### 追記(マイルストーン1実装時): `chardetng`を不採用に変更

CLIプロトタイプ実装中のテストで、`chardetng`の統計的判定はファイル名程度の短いバイト列では信頼性が低いことが判明した。具体例: 半角カナを含むShift-JISファイル名「ﾃｽﾄ_日本語ファイル.txt」を`chardetng`は「Big5」（中国語繁体字）と誤判定する。

代わりに、**生バイト列を実際に`encoding_rs`でShift-JISとしてデコードしてみて、エラーなく成功すればShift-JISと確定する**方式に変更した。失敗した場合のみCP437として扱う。この方式は対象v1の3エンコーディング(UTF-8はGPBフラグで確定/Shift-JIS/CP437)という閉じた選択肢に対しては決定的に働き、統計的推測より短い文字列で安定する。対象ユーザー（日本の学校・自治体）が本物のCP437(DOS罫線文字)ファイル名を送ってくることは実質的に無いため、「Shift-JISとして解釈可能なら常にShift-JIS優先」という判断が実用上正しい（既知の限界: CP437由来のバイト列がたまたまShift-JISとしても有効な列になるケースでは誤ってShift-JISとして解釈される。対象ユーザーには影響しない想定）。

結果、`chardetng`クレートへの依存は不要になった。実装は`src/encoding.rs`の`decode_entry_name`を参照。

## 技術スタック

| 用途 | 採用 |
|---|---|
| ZIP読み書き | `zip`クレート |
| エンコーディング判定 | `encoding_rs`でのShift-JISストリクトデコード試行（エントリ単位）。`chardetng`は実装時の検証で不採用に変更（上記追記参照） |
| エンコーディング変換 | `encoding_rs`（CP437は非公開APIのため独自テーブルを`src/encoding.rs`に実装） |
| GUI | `egui`/`eframe`（webview非依存、静的バイナリで完結） |
| ファイルダイアログ | `rfd` |
| 配布形式 | `.deb` / AppImage |
| シェル統合 | Nautilusスクリプト、`.desktop`（MIME: `application/zip`） |

## 当面のマイルストーン

1. CLIプロトタイプでエンコーディング判定ロジックの動作確認（解凍側、エントリ単位） — 完了。`src/main.rs` + `src/encoding.rs`。`cargo test`で判定ロジックを検証済み。1つのZIP内にShift-JIS(半角カナ含む/含まない)とUTF-8フラグ付きエントリを混在させた実データでも正しく判定できることを確認済み（rc-zipが失敗するケース）
2. CLIプロトタイプでZIP圧縮（UTF-8ファイル名）の動作確認
3. `egui`で最小GUI（ドラッグ&ドロップ→解凍／圧縮）
4. Nautilus「ここに解凍」「ここを圧縮」スクリプト連携
5. `.deb`/AppImageパッケージング
