# 0002. 文字コード判定は`chardetng`ではなく、Shift-JISストリクトデコード試行方式を採用

## ステータス

Accepted（[0001](./0001-zip-crate-over-rc-zip.md)の一部を修正）

## 背景

マイルストーン1（CLIプロトタイプ）実装時、[0001](./0001-zip-crate-over-rc-zip.md)で採用予定だった`chardetng`によるエントリ単位の統計的判定を実装してテストしたところ、ファイル名程度の短いバイト列では信頼性が低いことが判明した。

具体例: 半角カナを含むShift-JISファイル名「ﾃｽﾄ_日本語ファイル.txt」を`chardetng`は「Big5」（中国語繁体字）と誤判定する。

さらに検討の過程で、`rc-zip`由来のCP437判別ヒューリスティック（chardetngがShift-JISと判定しても、生バイト列に0xB0..=0xDF域のバイトが1つも無ければCP437とみなす）を単純に踏襲する案も検討したが、これは半角カナを含まない純粋な漢字・ひらがなのファイル名（学校・自治体からのファイルで典型的なパターン）を誤ってCP437と判定してしまう欠陥があり、採用しなかった。

## 決定

生バイト列を実際に`encoding_rs`でShift-JISとしてデコードしてみて、**エラーなく成功すればShift-JISと確定する**方式に変更した。失敗した場合のみCP437として扱う（実装: `src/encoding.rs`の`decode_entry_name`）。

この方式は対象v1の3エンコーディング（UTF-8はGPBフラグで確定／Shift-JIS／CP437）という閉じた選択肢に対しては決定的に働き、統計的推測より短い文字列で安定する。対象ユーザー（日本の学校・自治体）が本物のCP437（DOS罫線文字）ファイル名を送ってくることは実質的に無いため、「Shift-JISとして解釈可能なら常にShift-JIS優先」という判断が実用上正しい。

## 既知の限界

CP437由来のバイト列がたまたまShift-JISとしても有効な列になるケースでは、誤ってShift-JISとして解釈される。対象ユーザーには実質影響しない想定。

## 影響

- `chardetng`クレートへの依存は不要になり、`Cargo.toml`から削除した。
- テストは`src/encoding.rs`の`#[cfg(test)] mod tests`を参照（UTF-8フラグ分岐、半角カナ入り/なしShift-JIS、CP437フォールバック、複数エンコーディング混在の独立判定の5件）。
