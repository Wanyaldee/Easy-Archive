# 0008. GitHub Release連携アップデート機構

## ステータス

Accepted（実機検証（ハッピーパス）済み。チェックサム不一致・PolicyKit認証キャンセル時のエラー表示は未検証。詳細は「実機検証結果」参照）

## 背景

バージョンを重ねていくにつれ、対象ユーザー（日本の学校・自治体の非エンジニア職員）が新しいリリースの存在に気づく手段がなかった。ADR 0007の時点では`.deb`をGitHub Releaseへ手動配布するのみで、更新は「GitHubを見に行って手動でダウンロードし直す」以外の方法がなかった。

対象ユーザーはターミナル操作をさせない方針（ADR 0007）であり、かつ本機能の前提として利用者自身が自PCのsudo/管理者パスワードを持っている（Active Directory等で管理者権限を持たない共有PC運用はスコープ外）。この前提の下、GUIアプリ内から更新の検知・ダウンロード・インストールまで完結させることにした。

詳細な設計・データフロー・エラーハンドリング方針は設計書 [`docs/superpowers/specs/2026-09-16-github-release-auto-update-design.md`](../superpowers/specs/2026-09-16-github-release-auto-update-design.md) を参照。本ADRはそこに書かれた決定のうち、将来「なぜこうなっているのか」を問われそうな技術的決定を要約し、レビューで洗い出された既知の限界を記録するものである。

## 決定

### 1. `pkexec apt-get install -y <path>`を採用する（`dpkg -i`直接実行・カスタムpolkitアクション・独自APTリポジトリは不採用）

- `dpkg -i`ではなく`apt-get install -y <deb_path>`を使う。`apt-get`はローカル`.deb`ファイルを指定してもAPTの依存解決の仕組みに乗るため、将来`Depends`対象のライブラリが増えた場合の保険になる（`cargo-deb`の`Depends`は手動補完済み（ADR 0007決定4）だが、二重の安全策として）。
- `pkexec`はシェルを介さずプロセスを直接起動するため、引数はエスケープ不要でそのまま渡せる。
- PolicyKitの認証ダイアログはOS標準のものをそのまま使う。カスタムpolkitアクション定義（`/usr/share/polkit-1/actions/`への`.policy`ファイル配置とダイアログ文言のカスタマイズ）は追加しない。標準ダイアログはコマンドライン全体を表示するため非エンジニアには見慣れない文言になるが、機能上は問題なく、YAGNIとして将来の改善候補に留める。
- 独自APTリポジトリの構築は行わない。GitHub Releasesの`.deb`アセットをそのまま利用する。独自リポジトリの運用（署名鍵管理・ホスティング）は本機能のスコープに見合わないコストになる。

### 2. `ureq`（`reqwest`ではなく）+ `serde`/`serde_json` + `sha2`を新規依存として`crates/core`にのみ追加する

| クレート | 用途 | 採用理由 |
|---|---|---|
| `ureq` | HTTPS通信（GitHub API・ダウンロード） | rustls採用でOpenSSL等の追加ネイティブ依存が要らない。同期APIで、本プロジェクトが既に採用している「`std::thread::spawn` + `mpsc::channel`」方針（非同期ランタイムを持たない）と相性が良い。`reqwest`はasync前提でtokioランタイムを引き込むため、本プロジェクトの同期スレッド方針とは相性が悪く、YAGNIの観点でも見合わない |
| `serde` / `serde_json` | GitHub APIレスポンスのJSONパース | `assets`配列を含むネスト構造の手書きパースは壊れやすく、標準的な選択 |
| `sha2` | ダウンロードした`.deb`のSHA-256検証 | root権限で実行する前の完全性検証として必須（決定4も参照） |

いずれも既存の`quick-xml`/`zip`等と同じ依存階層になる`crates/core`に追加した（`crates/gui`ではない）。設計書のアーキテクチャ節にある通り、CLI側から呼ぶ予定は今のところないが、既存の`integration/`モジュールと同じ理由（GUI非依存に保つことでのテスト容易性。`crates/gui`はUIコードでユニットテストしづらい）でこの配置にした。

### 3. バージョン比較は`semver`クレートを使わず、手書きの`(u32, u32, u32)`タプル比較にする

本プロジェクトが発行するタグは`vX.Y.Z`のみでプレリリース識別子等は使わない。`X.Y.Z`を`.`で分割して`(u32, u32, u32)`にパースし、タプル比較するだけで「桁上がり（`0.9.0` < `0.10.0`）を文字列比較の罠なく正しく扱う」という要件を満たせる。`semver`クレートが提供するプレリリース識別子・ビルドメタデータ・範囲指定（`^`/`~`）等の機能は使う予定がなく、新規依存を追加する前にスコープが本当に必要としているかを確認するというCLAUDE.mdのYAGNI方針に照らして見送った。パースに失敗した場合（タグ命名規則が将来変わった等）は「更新なし」として扱い、エラーにはしない（起動時チェックを壊さないことを優先。`crates/core/src/update.rs`の`parse_version`/`is_newer`）。

### 4. パッケージ署名（GPG/minisign）は行わず、チェックサムのみで完全性を担保する

`.deb`と併せて`SHA256SUMS.txt`（`sha256sum`標準出力形式）をGitHub Releaseへアップロードし、`pkexec`実行前に`crates/core/src/update.rs`の`verify_checksum`でSHA-256を照合する（不一致ならインストールに進まない）。

**既知の限界（重要）**: このチェックサムは、ダウンロードが転送中に破損した、あるいはダウンロード経路上で改竄されたことを検知するだけである。GitHub Releaseにアップロードされる`.deb`自体がビルドパイプライン（GitHub Actionsワークフロー、あるいはそこから取得する依存クレート）の侵害によって差し替えられた場合、チェックサムファイルも同じパイプラインが生成するため、この仕組みは無力である。GPG/minisign等によるコード署名（ビルド環境とは別に保管された鍵で署名し、クライアント側がその鍵で検証する）を行っていないため、この種の侵害を検知する手段は本機能にはない。署名鍵の生成・保管・ローテーションは新たな運用コストを要するため、YAGNIとして今回は見送り、将来の課題として残す。

### 5. GUI再起動は`env::current_exe()`ではなく固定パス`/usr/bin/easy-archive-gui`を直接起動する

`crates/gui/src/main.rs`の`restart_application`:

```rust
fn restart_application() -> Result<(), String> {
    std::process::Command::new("/usr/bin/easy-archive-gui")
        .spawn()
        .map_err(|e| format!("再起動に失敗しました: {e}。アプリを手動で再起動してください。"))?;
    std::process::exit(0);
}
```

`.deb`インストール直後は`env::current_exe()`（`/proc/self/exe`）が、置き換え前の（既にunlinkされた）inodeを指したままになりうる。これはADR 0007の`resolve_cli_binary_path`が`env::current_exe()`をそのままCLIバイナリパスとして使わなかった理由（GUIプロセス自身のパスとCLIバイナリのパスが異なる、という別の問題ではあるが）と同種の「実行中バイナリ自身のパス解決は`.deb`インストールのタイミング次第で信頼できない」という教訓に基づく。`.deb`は`easy-archive-gui`を常に`/usr/bin/`へ設置する（ADR 0007決定3の`assets`）ため、この固定パスは`.deb`配布という前提の下では安全に決め打ちできる。

起動に失敗した場合（当該パスが存在しない開発ビルド環境など）は、黙ってプロセスを終了せず、手動再起動を促すメッセージをGUIのステータス表示に出す。非エンジニアの対象ユーザーにとって、ウィンドウが説明なく消える挙動はクラッシュに見えるため。

## 既知の限界

- **APT以外のパッケージマネージャーは対象外**（DNF/Pacman等）。CLAUDE.mdの対象OS方針（Ubuntu系限定）と一致。設計書「既知の限界」参照。
- **更新バナーに「非表示にする」ボタンがない**: `Available`/`Error`状態は「アップデートする」「再試行」ボタンのみで、無視して閉じる手段がない。設計書のスコープには含まれておらず、次回起動時チェックまで消えない。
- **GitHub APIの未認証レート制限（60リクエスト/時間/IP）**が、実運用ターゲット（学校PC、共有NAT環境）で始業時間帯の一斉起動時に問題になりうる。設計書「既知の限界」に詳細と将来対応案（24時間キャッシュ、静的URLへの切り替え）を記載した。
- **TOCTOU対策**: `download_and_install`は`.deb`をプロセスIDを含む専用の一時ディレクトリ（`0o700`権限）に書き込んでから`pkexec`へ渡す。固定の予測可能なパス（`std::env::temp_dir().join("easy-archive-update.deb")`のような共有`/tmp`直下の固定名）は、他のローカルユーザーが先回りしてファイル/ディレクトリを作成し、root権限インストール対象を乗っ取る余地を残すため避けた。

## 実機検証結果（Zorin OS Core、VirtualBox仮想環境）

ユーザーがZorin OS Core（VirtualBox仮想マシン）上で以下を確認した（2026-09-16）。

- `v0.1.1`の`.deb`をインストールした状態でGUIを起動し、起動時バナーで`v0.1.2`（本機能の検証のためだけに機能変更なしで発行したリリース。GitHub Release本文にもその旨を明記した）が検知されることを確認した。
- 「アップデートする」ボタン押下→ダウンロード→PolicyKitの認証ダイアログでの認証→`apt-get install`成功→「再起動する」ボタンでの再起動、という一連のハッピーパスが正常に動作した。

**検証中に判明した教訓（テスト設計上の注意点）**: 当初、本機能の実装前にビルド・配布された`v0.1.0`をインストールして検証しようとしたが、バナーが一切表示されなかった。原因は`v0.1.0`のバイナリには`update`モジュール自体が含まれておらず（`git show v0.1.0:crates/core/src/lib.rs`で`pub mod update;`が存在しないことを確認済み）、更新検知ロジックそのものが存在しなかったこと。「更新を検知する側」のバイナリは本機能を持つビルド（`v0.1.1`以降）である必要があり、それより新しいリリースが存在して初めてハッピーパスを検証できる。次回以降、この機能に関わる実機検証を行う際は、検知される側に既に本機能を含むバージョンをインストールした上で、それより新しいリリースを用意すること。

**今回未検証（次回以降の課題）**:
- チェックサムを意図的に不一致にした場合に、インストールが中断されエラー表示されること
- PolicyKitの認証ダイアログをキャンセルした場合に「認証がキャンセルされました」と表示されること

- 新規作成: `crates/core/src/update.rs`（バージョン比較・GitHub APIレスポンス解析・ダウンロード・チェックサム検証・`pkexec`実行）、`.github/workflows/release.yml`（タグpush時に`.deb`ビルド・チェックサム生成・GitHub Releaseへのアップロードを行う。ADR 0007で「対象外」としていたアップロード自動化を本機能でスコープに含めた）、本ADR。
- 変更: `crates/gui/src/main.rs`（起動時アップデートチェック・`update_banner`・インストール導線・`restart_application`を追加）、`docs/superpowers/specs/2026-09-16-github-release-auto-update-design.md`（本機能の設計書。既知の限界にレート制限・チェックサムの限界に関する追記あり）、`.github/workflows/ci.yml`（コメントのみ。`release.yml`とのビルド手順重複について注記を追加）。
- `crates/core/Cargo.toml`: `ureq`・`serde`・`serde_json`・`sha2`を追加（決定2）。
