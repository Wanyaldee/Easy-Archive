# 0001. ZIP読み書きは`zip`クレート＋自前のエントリ単位判定を採用し、`rc-zip`は不採用

## ステータス

Accepted（`chardetng`採用の部分は [0002](./0002-drop-chardetng-strict-decode.md) で修正）

## 背景

文字コード自動判定つきZIP解凍・圧縮ツールのコアとして、`rc-zip`（bearcove/rc-zip, 検証時点でv5.4.1）を採用候補として技術検証した。検証観点は判定粒度・信頼度スコアの取得可否・ライセンス・API安定性・対応エンコーディング範囲・依存の重さ・書き込み対応の有無。

`rc-zip`のソースコードを直接確認し、以下の結論に至った。

| 項目 | 結果 |
|---|---|
| 判定粒度 | **アーカイブ全体で1回のみ**（`fsm/archive.rs`で全非UTF8エントリの名前/コメントをまとめて`chardetng`にfeedし、1つの`Encoding`を全エントリへ一律適用）。エントリ単位ではないため、1つのZIPに複数言語のファイル名が混在すると破綻する |
| 信頼度スコア | `chardetng::EncodingDetector::guess()`は`Encoding`型を1つ返すのみで、confidence値を返すAPIは存在しない |
| ライセンス | `Apache-2.0 OR MIT`（問題なし） |
| API安定性 | v5.4.1、活発にメンテナンスされている（2025年11月だけで6回リリース）が、メジャーバージョンが2→5まで進んでおり過去に破壊的変更あり |
| 対応エンコーディング | `Encoding` enumは`Utf8` / `Cp437` / `ShiftJis`の3種のみ。GBK・EUC-JP等は非対応 |
| 依存の重さ | `winnow`, `chardetng`, `encoding_rs`, `oem_cp`, `chrono`等。定性的に軽くはない。正確なバイナリサイズ影響は実測が必要 |
| 書き込み対応 | **非対応**（READMEに"as of now, rc-zip does reading only"と明記） |

## 決定

「エントリ単位判定」「信頼度スコア」の両方で要件を満たさず、`rc-zip`をそのまま使うと「複数言語混在ZIPで判定が破綻する」「GUI側で自動判定の自信度を表示できない」という当初の懸念がそのまま顕在化する。加えて`rc-zip`は読み取り専用なので、いずれにせよ圧縮側には別クレートが要る。

`zip`クレート（MITライセンス）は以下の理由で読み書き両方を任せられる:

- 読み書き両対応（圧縮もカバーできる）。
- `ZipFile::name_raw()`でファイル名を**生バイト列**（未デコード）のまま取得可能 → エントリごとに個別に文字コード判定できる。

よって **展開・圧縮ともに`zip`クレートに統一し、エントリ単位の文字コード判定を自前実装する**（`rc-zip`の`fsm/archive.rs`にある判定ロジックを、アーカイブ全体ループからエントリ単位ループへ書き換える形で流用可能）。`rc-zip`自体は採用しない。

当初はこの自前実装の判定に`chardetng`を使う想定だったが、実装時に方針を修正した。詳細は[0002](./0002-drop-chardetng-strict-decode.md)を参照。

## 影響

- 依存クレートは`zip`（読み書き）＋文字コード変換用の`encoding_rs`のみで構成する。
- 判定ロジックの実装は`src/encoding.rs`の`decode_entry_name`。
